# ADR-0001: 음성 채점 비동기화 + 오브젝트 스토리지

> 상태: **Implemented** (2026-09-22, 운영 배포). 결정과 다르게 한 것·실측은 9절.
> 이력: 2026-09-17 근거 재정렬 · 2026-09-18 근거 ① 교체("분 단위" 폐기, S1 실측 7.6s) · 2026-09-19~21 1·2단계 구현 · 2026-09-22 측정·배포, 9절 추가
> 관련: `PROJECT.md` PracticeAttempt 설계 배경, `docs/hold.md`(S3/큐 보류 이력), `docs/performance/2026-08-31-500vu-reproduction-check.md`

## 1. 결정

**오디오는 클라이언트가 오브젝트 스토리지에 직접 올리고, 채점은 서버 워커가 맡으며, 클라이언트는 접수 응답만 받는다.** 구현체는 R2, 코드는 S3 API 기준.

두 단계로 간다.

| 단계 | 범위 | 상태 |
|---|---|---|
| 1 | 오브젝트 스토리지 업로드 전환 + **모의고사만** 비동기 | 완료 2026-09-21 (`270c51c`) |
| 2 | 콤보를 같은 경로로 이전, 동기 경로 제거 | 완료 2026-09-21 (`e9ebc82`, `7b9730a`) |

최종 형태는 **파이프라인 하나**다. 1단계에서 콤보가 동기로 남는 건 이행 중간 상태이지 유지할 구조가 아니다. 두 경로를 계속 두면 STT→채점→태깅→저장이 두 벌이 되고, 재시도·실패 처리·저장 모델까지 두 벌이 된다.

## 2. 근거 — 다섯 줄

```
① 접수 후 작업의 주인이 누구인가
   동기 = 클라이언트가 주인. 기다리고, 실패하면 사용자가 다시 낸다. 재시도·백오프가
   길어질수록 사용자 요청이 그만큼 물려 있고(nginx 60s), 연결이 끊기면 재시도도 같이 죽는다
   → 서버가 주인이어야 재시도·재처리·FAILED 확정을 통제할 수 있다 (비동기)
   ※ 원래 ①은 "모의고사가 분 단위라 요청 안에서 못 끝냄"이었다. Groq 무료 티어 현상이었음 —
     mock 3s+4.5s에서 15문항 병렬 7.6s 실측(2026-09-18, `performance/2026-09-18/s1-before.txt`).
     정상일 때 빠른 것과 안전한 것은 다르다. 속도는 근거에서 뺀다.

② 뒤에서 처리하려면 오디오가 요청보다 오래 살아야 함. 인메모리로 두면
   a) 서버 재시작 시 접수한 작업이 증발                        ← 유실
   b) 요청당 2MB 힙 적재 → 500VU에서 800MB/s → Full GC 3회/30초  ← 2026-09-11 측정
   → 프로세스 밖 저장소 필요

③ 서버가 재시도를 소유하면 실패할 때마다 오디오를 다시 읽어야 함
   → "처리 완료(재시도 포함)까지" 살아야 함. 요청 수명보다 훨씬 김. ②를 강화

④ 어떤 저장소인가
   a)만 풀 거면 NFS·공유 볼륨도 됨
   b)까지 풀려면 서버가 바이트를 아예 안 받아야 함
   → 클라이언트가 직접 올려야 함 → HTTP 인증 업로드(presigned URL) → 오브젝트 스토리지만 됨

⑤ 오브젝트 스토리지 중 무엇인가
   성질은 전부 같음. R2 = 무료 10GB, egress 0, 기존 Cloudflare 계정, 운영 부담 0
   S3 API라 교체 가능. 아키텍처 이유가 아니라 살림 이유
```

근거가 서로 독립인 두 갈래(유실 / 힙)라 하나가 무너져도 선다. "NFS로 되지 않나"에는 b)로, "힙을 늘리면 되지 않나"에는 a)로 답한다.

**R2와 비동기가 각각 무엇을 푸는지 섞지 말 것.** R2는 힙(b)과 유실(a)의 절반 — 오디오가 남아 *재처리가 가능*해진다 — 을 푼다. 재시작 뒤 "이 attempt 아직 안 끝났다"를 기억하고 다시 돌리는 주체는 R2가 아니라 잡 테이블+워커(비동기)다. "R2 + 동기"로도 힙은 풀리지만 완료율 100%(이탈·재시작 포함)와 ①은 못 푼다.

**동기/비동기는 클라이언트–서버 경계의 얘기다.** 서버–LLM/STT 경계는 항상 동기(HTTP 호출 후 대기)이고 바꿀 대상이 아니다. 비동기화는 "LLM을 기다리는 주체"를 클라이언트에서 서버 워커로 옮기는 것이다.

### 비동기 기준 — 제품 언어로

기준은 처리 시간이 아니다. **외부 호출이 느려지거나 실패했을 때 누가 책임지는가.** 정상일 때는 동기도 충분히 빠르다(모의고사 15문항 병렬 7.6s). 문제는 정상이 아닐 때다.

- 모의고사부터 옮기는 이유: 15문항 = 이탈·재시작 시 잃는 게 가장 크고, 요청당 파일 15개라 힙 증폭기다.
- 콤보는 1단계에서 동기로 둔다: 잃는 게 3문항이고, 파이프라인을 두 벌로 만들지 않으려면 한쪽을 먼저 검증한 뒤 옮기는 게 맞다. (원래는 "제공자에 따라 5~10초 vs 2분"으로 갈렸는데, 종량제 가정 아래선 속도 차이가 이유가 아니다.)

면접에서 말할 근거 네 개.

1. 처리 시간 상한을 우리가 통제하지 못한다 — 외부 API, rate limit, 장애. 동기는 그 시간이 곧 사용자 대기이고, 재시도가 길어지면 연결이 먼저 끊긴다.
2. 빠른 것과 안전한 것은 다르다 — 정상 7.6s여도 그 사이 이탈·재시작이면 채점 전부 유실(전환 전 완료율 0%).
3. 부분 결과에 가치가 있다 — 15문항이 각자 끝나는데 가장 느린 하나에 전부 묶일 이유가 없다.
4. 실패 처리를 사용자에게 시키지 않는다 — 지금은 "2번 문항 실패, 다시 제출하세요"를 사용자가 한다.

### 검토했다가 제외한 것

| 선택지 | 제외 이유 |
|---|---|
| 서버 로컬 디스크 + 볼륨 | 서버가 바이트를 계속 받아야 해서 힙(②b) 이득이 없다. 호스트에 묶여 스케일아웃 경로가 막힌다 |
| NFS / EFS 공유 파일시스템 | 유실(②a)은 풀리지만 브라우저가 직접 못 올려서 힙(②b)이 그대로다 |
| DB BLOB | 직접 업로드 불가. 1MB × N BLOB은 MySQL 백업·복제 부담 |
| 힙 유지 + 세마포어 | 벽을 없애는 게 아니라 옮기는 것 |
| 인메모리 큐 | 202 약속 뒤 재시작하면 작업이 조용히 증발. 오디오가 밖에 있어도 "누가 미완료인지"를 잊는다 |
| MinIO 자체 호스팅 | 정당한 대안. 외부 의존을 줄이는 대신 컨테이너·백업·호스트 종속을 진다. 지금은 R2가 더 싸서 제외 |

## 3. 보관 — R2를 쓰는 이유가 아니라 "올린 김에 얼마나 둘 것인가"

"오디오 보관"은 하나의 결정이 아니라 서로 다른 문제 셋이다. 따로 놓으면 답이 다르다.

| 문제 | 결정 | 기간 | 근거 |
|---|---|---|---|
| **처리용 임시 저장** | 필수 | 처리 완료까지 | 2절 ②③. 나머지가 전부 "안 함"이어도 남는다 |
| **운영 근거** | 필요 | **30일** | "채점 이상해요"에 원음 없이는 STT 오류인지 채점 오류인지 못 가린다. STT 모델 교체 시 실제 답변으로 회귀 검증 |
| **다시 듣기** | 보완 기능으로 | 30일에 맞춤 | 우리 피드백은 텍스트 인용(quote→fix)으로 "뭘 말했나"를 준다. 다시 듣기는 우리가 채점 안 하는 "어떻게 말했나"(억양·속도)를 사용자가 스스로 듣게 하는 것. 핵심 기능 아님. 유료화 시 보관 기간이 플랜 차별 요소가 될 수 있다 |

**파일이 필요 없는 것**: 통계·분석·코칭은 점수·태그·STT 텍스트로 전부 되고 이미 DB에 영구 보관 중이다. LLM 교체 검증도 STT 텍스트만으로 된다. 원음이 필요한 재처리는 STT 교체 시뿐이고, 30일 운영 보관에 포함된다.

**보관의 비용은 돈이 아니라 의무다.** 음성은 개인정보다. 보관 목적·기간 고지, 기간 만료 시 삭제(R2 라이프사이클 규칙), **탈퇴·삭제 요청 시 즉시 삭제**. "처리 후 즉시 삭제"는 반대로 프라이버시 셀링 포인트가 될 수 있다 — 포지셔닝 선택이며, 지금은 30일로 간다.

## 4. 구조

```
① 클라 → 서버   POST /attempts/{id}/upload-urls      → presigned PUT URL × N
② 클라 → R2     PUT 오디오 × N                       (서버 안 거침)
③ 클라 → 서버   POST /attempts/{id}/submit {keys}    → 202, attempt 상태 QUEUED
④ 워커          잡 테이블에서 QUEUED 집음 → R2 읽음 → STT → 채점 → 태깅
                → 문항별로 즉시 FeedbackResult 저장, 문항 상태 갱신
                → 전부 끝나면 attempt 상태 COMPLETED
⑤ 클라 → 서버   GET /attempts/{id}                   → 상태 + 완료된 문항 결과  (폴링)
                또는 GET /attempts/{id}/stream        → SSE로 문항별 push       (2차)
```

- **잡 상태는 DB.** attemptId, R2 키 목록, 문항별 상태·시도 횟수, 진행률. 작은 메타데이터라 부담 없고, 재시작 후 워커가 미완료 잡을 주워서 이어간다.
- **워커는 단일 인스턴스 안의 가상 스레드 풀 + DB 폴링.** 외부 큐(Kafka 등)는 지금 규모에서 오버엔지니어링. `docs/hold.md`의 판단 유지.
- **결과 전달은 폴링부터.** SSE는 문항별 스트리밍 UX가 필요할 때 얹는다. SSE 연결 맵은 인메모리라 단일 인스턴스 전제이며, 다중 인스턴스면 Redis pub/sub이 필요하다 — 지금은 범위 밖.

### 직접 업로드가 우회하는 것 — 반드시 다시 세울 것

2026-09-02에 세운 업로드 방어선(브라우저 2분 → nginx 64M → 톰캣 4MB/64MB → 컨트롤러 4MB)은 **전부 서버를 거칠 때의 것이다.** 클라이언트가 R2에 직접 올리면 하나도 안 거친다.

- **크기 상한**: presigned URL 발급 시 `content-length-range` 조건(4MB)을 박는다. 못 박는 클라이언트면 `③ submit` 시 서버가 R2에 `HEAD`로 크기·타입을 확인하고 초과분은 거절 + 삭제.
- **발급 권한**: presigned URL은 로그인한 소유자의 attempt에만, 문항 수만큼만, 짧은 만료(예: 10분)로 발급한다. 키는 서버가 정한다(`attempts/{id}/q{n}.webm`) — 클라이언트가 키를 고르게 두지 않는다.
- **고아 객체**: ②까지 하고 ③이 안 오면 객체만 남는다. 라이프사이클 규칙으로 미제출 프리픽스는 24시간 뒤 삭제.

### 서버 소유 재시도의 안전장치

지금은 사용자가 재제출하니 사람이 멈춘다. 워커가 재시도하면 **버그 하나로 아무도 안 보는 채 외부 API 할당량을 다 태울 수 있다.**

- 문항별 최대 시도 횟수(3). 초과 시 문항 상태 `FAILED`로 확정하고 더 안 건드린다.
- attempt에 `FAILED` 문항이 있으면 attempt는 `COMPLETED_WITH_FAILURES`. 사용자에게 어느 문항이 실패했는지 보여주고, 재시도는 **사용자가 명시적으로** 누를 때만.
- 워커 루프에 전체 실패율 서킷: 최근 N건 중 실패 비율이 임계를 넘으면 외부 API를 잠시 안 부른다. 2026-08-31에 실측한 재시도 증폭(STT 43건, 429 21회)의 워커 버전을 막는 것.

## 5. 연쇄로 바뀌는 것

비동기로 정하면 자동으로 딸려온다. 따로 결정할 것 없이 한 묶음이다.

| 지금 | 바뀐 뒤 | 이유 |
|---|---|---|
| `POST /finalize`가 세션의 결과를 DB에 한 번에 저장 | **finalize 제거.** 워커가 문항별로 즉시 저장, 완결은 상태값 | 완결 판정 주체가 클라이언트에서 워커로 넘어간다. 워커가 스스로 아는데 클라이언트에게 물을 이유가 없다 |
| "완결된 것만 DB에" 로 통계 정합성 보장 | "즉시 저장 + 완결 attempt만 필터" 로 보장 | 저장 로직은 단순해지고 조회 로직에 필터가 들어간다. `/analytics`, 코칭 열람 조건, `/today` 진행률이 전부 영향받는다 |
| attempt 상태 Caffeine(2시간, 10k 상한) | DB | 202 약속을 재시작 후에도 지켜야 한다. 부수 효과로 단일 인스턴스 제약 하나가 풀린다 |
| 실패 문항을 클라이언트가 재제출 | 워커가 재시도(상한 있음), 클라이언트는 최종 상태만 | 근거 4번 + 4절 안전장치 |
| `beforeunload` 이탈 경고 | 불필요 | 이탈해도 처리가 계속되고 결과가 남는다 |
| 서버 측 업로드 상한 4겹 | presigned 조건 + HEAD 검증으로 재구성 | 4절. 기존 4겹은 콤보가 동기로 남는 1단계 동안만 유효 |

**미완결 attempt를 저장하게 되면 이탈 분석 데이터가 생긴다.** 지금 구조는 "3문항 중 2개 하고 나감"을 통째로 버린다. 프로덕트 관점에서는 이쪽이 오히려 이득이다.

## 6. 정직하게 남는 것

- 단일 인스턴스 전제는 워커·SSE 맵에 여전히 남는다. 잡 테이블을 DB에 두면 다중 인스턴스 워커는 `SELECT ... FOR UPDATE SKIP LOCKED`로 확장 가능하지만 지금은 안 한다.
- Groq TPM 8K에서는 비동기여도 모의고사 1건에 10분이다. 비동기는 그 10분을 사용자 대기에서 떼어낼 뿐 줄이지는 않는다. 처리량 자체는 제공자 결정이다.
- R2 CORS·자격증명 관리, 폴링 간격은 구현 시 정한다.

## 7. 검증 — SLO 기준으로

이 설계가 지켜야 할 SLO와 시나리오는 `docs/performance/slo.md`. 요지:

- 사용자 1명 기준: 접수 응답 p95 < 500ms, 접수된 제출 처리 완료율 100%(이탈·재시작 포함), 콤보 첫 문항 결과 < 10s, 모의고사 완료 < 1분
- 장애 시: 외부 API 실패 45% 주입 시 호출 증폭 ≤ 1.65배(설계대로일 때의 이론값), 서버 OOM 0·503 거절
- 피크: 동시 제출 30건(국내 상위 영어 학습 앱 피크 추정치의 약 2배)에서 위 조건 유지
- SLO는 원하는 수준이지 현재 배포 수준이 아니다. Groq 무료 티어 미달 항목은 배포 주석으로 분리
- 500VU는 SLO가 아니라 한계 탐색. 전환 전(Full GC 3회/30초) 대비 전환 후를 같은 조건으로 비교

전환 **전** 수치를 지금 코드로 먼저 재두고, 구현 후 같은 시나리오를 돌려 전/후 표를 만든다.

## 8. 이력서 한 줄 (확정)

> 음성 채점 요청을 동기적으로 응답하던 중, API 지연이 응답 지연 발생 & 사용자 중간 이탈 시 결과 유실 → 객체저장소 R2와 별도 워커로 요청과 채점을 비동기 처리해 즉시 응답 및 결과 보존

구현·배포됐으므로 "전환"으로 쓴다.

## 9. 결과 — 결정대로 한 것, 다르게 한 것, 숫자

### 결정대로

- 클라이언트 → R2 직접 PUT(presigned, 크기·타입이 서명에 박힘 — 틀리면 R2가 403), 서버는 파일을 받지 않는다. 옛 업로드 방어선(nginx 64M·톰캣·컨트롤러)은 코드와 함께 제거, nginx 본문은 1M.
- 잡 상태는 DB(`scoring_job` + `scoring_job_item`), 워커는 단일 인스턴스 가상 스레드 + 1초 DB 폴링, 문항이 저장·재시도·실패의 단위. 3회 → `FAILED`, 잡은 `COMPLETED_WITH_FAILURES`. 실패율 서킷(20건 중 80%, 30초). 미제출 객체는 `pending/` 라이프사이클 1일.
- 결과 전달은 숏폴링 2초. SSE는 안 했다(폴링 응답이 SSE 재연결 스냅샷을 겸하도록 설계만).
- finalize 제거. 완결 판정은 워커(마지막 문항이 잡 행 락 아래서 닫는다).

### 다르게 한 것 — 왜

| 결정 | 실제 | 이유 |
|---|---|---|
| ③ `POST /attempts/{id}/submit {keys}` | `POST /api/scoring-jobs {attemptId}` → 202 + Location, `GET /api/scoring-jobs/{id}` | 접수는 새 리소스(잡)의 생성이라 REST로는 동사 URL이 아니라 컬렉션 POST. 키는 클라이언트가 보내지 않는다 — 서버가 같은 규칙(`pending/{attemptId}/q{n}.webm`)으로 다시 만든다 |
| 잡 행을 attempt 생성 시 만든다고 읽힐 수 있었음 | **잡 행은 submit(202) 시점에** 생성. 그 전(문제 조립·녹음·업로드)은 Caffeine attempt | 약속은 202에서 시작한다. 그 전 상태는 잃어도 무해(사용자가 다시 시작) — 저장소를 늘리려면 그 순간의 약속을 말할 수 있어야 한다. 구현 중 한 번 잘못 갔다가 되돌림 |
| "attempt 상태 Caffeine → DB" | Caffeine은 submit 전까지 남는다. DB로 간 건 잡뿐 | 위와 같은 이유. Caffeine의 상태 전이(IN_PROGRESS→FINALIZING→SUBMITTED)는 중복 접수 차단에 재사용 |
| submit 시 R2 HEAD로 크기 확인 | 안 한다 | 크기가 서명에 박혀 있어 초과분은 애초에 안 올라간다. 안 올라간 파일은 워커가 읽을 때 404로 FAILED — 접수는 DB만 쓰고 끝나야 202가 빠르다 |
| presigned URL 발급 시점 미정 | **녹음이 다 끝난 뒤**(제출 버튼) | 서명에 크기가 들어가므로 파일이 있어야 발급 가능. 화면 열 때 발급 불가 |
| `FeedbackResult.member` nullable(dev attempt) | dev 프로파일 전용 테스터 회원(`DevTesterMember`) | 운영 스키마에 nullable을 넣지 않기 위해 |
| 워커 동시 상한 미정 | 설정값, 기본 60 | 피크 "동시 제출 30건"을 문항 단위로 바꾸면 콤보 ~90 — 30명 실측에서 60이면 큐 0. 모의고사 피크(450문항)엔 90 필요, DB 보호 뒤에 (`performance/2026-09-22/slots-sweep.md`) |
| 워커가 잡을 집는다고 읽힐 수 있었음 | **문항** 단위로 집고 제출 건끼리 섞인다 | 공정성 — 15문항 모의고사 하나가 뒤의 콤보 3문항을 다 기다리게 하지 않는다 |
| 처리 후 `attempts/`로 옮겨 30일 보관(3절) | 아직 안 함 — `pending/` 1일 후 삭제 | 후속. 결과 행에 오디오 키가 없어 재청취 기능이 생길 때 같이 |
| STT 실패 문항의 사용자 재시도 버튼 | 아직 없음 | 후속 API(`POST /api/scoring-jobs/{id}/items/{index}/retries`). 지금은 FAILED 카드까지만 |

구현 중 잡은 것: 워커엔 OSIV가 없어 문항 조회에 트랜잭션 필요 / 마지막 문항 둘이 동시에 끝나면 아무도 잡을 안 닫는 경쟁 → 잡 행 `PESSIMISTIC_WRITE` / 처리 중 죽은 프로세스의 PROCESSING 문항은 기동 시 즉시 회수(5분 스윕만으론 "재시작 포함 1분"이 안 선다) / STT 성공분은 `sttText`에 남겨 재시도·재시작 후 STT를 다시 부르지 않는다(2026-08-31 자가 429 재발 방지).
