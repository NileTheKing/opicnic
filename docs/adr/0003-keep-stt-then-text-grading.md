# ADR-0003: 채점은 STT → 텍스트 채점 두 번 호출을 유지한다 (멀티모달 한 번 호출은 보류)

> 상태: **Accepted** (2026-10-30, 변경 없음)
> 관련: `docs/performance/2026-10-07-grading-calibration/README.md` "멀티모달 비교" 절(측정), ADR-0001(비동기 채점)

## 맥락

지금 채점은 외부 호출 두 번이다. Groq whisper-large-v3로 받아쓰고(STT), 그 글을 Gemini 3.5 Flash-Lite로 채점·태깅한다. Gemini는 오디오를 직접 받으므로 받아쓰기와 채점을 한 번에 할 수도 있다. 이 경우 STT 단계와 Groq 의존이 사라진다.

검토 계기: 단계가 두 개라 외부 제공자별 속도 제한·서킷을 따로 두려면 큐를 단계별로 나눠야 한다는 논의(2026-10-30). 단계를 나누기 전에 "단계를 아예 없애는 선택"을 먼저 따졌다.

측정(2026-10-30, 검증용 기준 답 21개를 macOS TTS로 읽힌 음성, 각 1회, 운영 프롬프트·스키마·등급 규칙 그대로):

| 경로 | 정답 등급(범위) 적중 | 받아쓰기 WER 평균 / 최대 | 입력 / 출력 토큰 | LLM 응답 시간 |
|---|---|---|---|---|
| 원문 텍스트 채점(기준선) | 19 / 21 | 0 | 3,266 / 702 | 3.2초 |
| Whisper → 텍스트 채점(지금) | 16 / 21 | 2.9% / 16.7% | 3,268 / 717 | 3.2초 + STT |
| 음성 직접(멀티모달) | 18 / 21 | 2.4% / 8.3% | 4,020 / 838 | 5.1초 |

- 받아쓰기 차이는 대부분 숫자 표기(seven → 7). 두 경로 모두 문법 오류를 고쳐 쓰지 않았다.
- 등급 차이 2~3건은 1회 실행으로 구분되지 않는다(같은 원문 재채점도 이만큼 흔들린다).
- 음성은 평균 32초(8~72초). TTS라 실제 말보다 빠르고 발음이 깨끗하다.

비용(종량제, 문항 하나, 채점 + 태깅). Gemini 3.5 Flash-Lite는 입력 100만 토큰당 $0.30(텍스트·오디오 같은 값), 출력 $2.50. 오디오는 초당 32토큰. Whisper는 turbo 시간당 $0.04(요청당 최소 10초)를 썼다. 서드파티 정리 값이고, 우리가 쓰는 whisper-large-v3 단가는 확인하지 못했다.

| 답변 길이 | 멀티모달 / 지금 |
|---|---|
| 이번 세트(평균 32초, 실측 토큰) | 약 +5% |
| 모의고사 답변 80초(오디오 2,560토큰, 받아쓰기 출력 약 260토큰 가정) | 약 +11% |

비용의 대부분(약 45%)은 채점 출력이라 어느 쪽이든 같다.

무료 등급 한도(2026-10-30 확인):
- Gemini 3.5 Flash-Lite: 분당 15회, 분당 입력 25만 토큰, 하루 500회 (AI Studio).
- Groq whisper-large-v3: 하루 2,000회(응답 헤더 `x-ratelimit-limit-requests`), 분당 20회(429 본문 실측). 오디오 시간당 7,200초 / 하루 28,800초(문서 값, 헤더로는 확인 안 됨).
- 모의고사 1회(15문항, 80초)는 Gemini 30회(채점 15 + 태깅 15), 지금 방식은 Groq 오디오 1,200초가 더 든다. 하루 상한은 두 방식 모두 Gemini 하루 500회 ÷ 30 = 약 16회. Groq 오디오 한도(하루 약 24회)는 먼저 걸리지 않는다. 멀티모달의 토큰(모의고사 1회 분당 약 4.5만)도 분당 한도 안이다.

## 결정

지금 구조(STT → 텍스트 채점)를 유지한다. 멀티모달 한 번 호출은 비용이나 품질 개선 수단이 아니라 **발음·유창성 피드백 기능**을 만들 때의 선택지로 남긴다.

## 근거

- 품질·하루 상한·비용·응답 시간이 모두 비슷해서 바꿀 이득이 측정되지 않았다. 바꾸려면 프롬프트·스키마 변경과 채점 기준 재보정(2026-10-07 보정 실험 전체)을 다시 해야 한다.
- 가장 큰 위험을 아직 재지 못했다: 실제 학습자(비원어민) 음성에서 LLM이 들린 그대로 받아쓰는가. 그럴듯한 문장으로 고쳐 적으면 문법 오류가 사라져 채점이 후해진다. OPIc 채점에서 가장 나쁜 실패다. Whisper는 전용 STT라 이 위험이 상대적으로 낮다고 알려져 있다(이 서비스 음성으로는 확인 안 함).
- 지금 구조는 STT 결과를 저장해 채점만 다시 할 수 있다(`ScoringJobItem.sttText`). 멀티모달은 채점이 실패하면 음성부터 다시 보낸다.
- 장애 면에서는 멀티모달이 낫다(제공자 하나만 의존). 하지만 지금도 Gemini가 죽으면 결과를 못 주므로 사용자가 보는 가용성 차이는 Groq 장애분뿐이다.
- 멀티모달로 갈 만한 이유는 기능이다. 지금 유창성은 단어 수로만 계산한다(`FeedbackService.computeFluencyScore`). 음성을 직접 보면 끊김·말 속도·발음을 채점과 피드백에 쓸 여지가 있다(측정 안 함).

## 결과

- 코드 변경 없음.
- 다시 볼 조건: (1) 발음·유창성 피드백을 기획할 때, (2) Groq STT 단가나 한도가 바뀌어 비용·상한 차이가 커질 때, (3) 단계별 큐로 나누는 작업을 시작하기 전.
- 다시 볼 때 먼저 할 측정: 실제 사람 녹음(학습자 억양·말더듬 포함) 몇 개로 Whisper와 멀티모달 받아쓰기를 비교해 문법 오류 보존을 확인한다. 스크립트 `docs/performance/2026-10-07-grading-calibration/multimodal_check.py`에 음성 파일만 바꿔 넣으면 된다.
- 한계: TTS 음성, 각 1회, whisper-large-v3 단가 미확인, 무료 한도는 2026-10-30 화면 기준.
