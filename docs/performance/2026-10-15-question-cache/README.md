# 문항 인메모리 캐시는 무엇을 아끼는가 — 2026-10-15

질문: 문항 캐시 두 개(`QuestionAssemblyService.setCache`, `PracticeAttemptService.questionCache`)를 끄고 켰을 때, 같은 부하에서 지연과 DB 사용이 얼마나 달라지나.

배경: 예전 메모의 "캐시로 p95 80% 개선 (20.5s → 3.73s)"은 비교가 성립하지 않는다. `docs/local/2026-06-11-question-cache-load-test.md`를 보면 캐시만의 효과는 p95 20.5s → 20.17s였고, 큰 폭의 감소는 `@Transactional` 제거에서 나왔으며, "전"은 500 VU, "후"는 100 VU였다. 이번에는 조건 하나(캐시 on/off)만 바꾸고 부하는 같게 했다.

## 결론

- **캐시의 효과는 있지만 작다.** 캐시는 요청 하나당 DB 문장 6개 중 1개(문항 세트 조회 SELECT)와, 채점 문항 하나당 문항 조회 SELECT 1개를 없앤다. 이 SELECT 하나의 DB 실행 시간은 평균 0.16~0.22ms다.
- **지연:** 동시 사용자 1명에서 start API p50이 1.18 → 0.84ms(약 0.3ms 감소)다. 30명까지는 두 번의 측정에서 방향이 엇갈리거나 편차 안이다. 60~100명(요청 사이 대기 없이 연속 호출, 커넥션 풀 50개가 꽉 찬 상태)에서만 캐시 켬이 일관되게 빠르다(p50 16~70% 감소, 처리량 +18~+240%, 두 번의 측정 사이 편차가 크다). "80% 개선" 같은 수치는 이 데이터로 뒷받침되지 않는다.
- **커넥션:** 요청당 커넥션 획득 횟수는 켬/끔 모두 1.0이다. 캐시를 켜도 `assemble()`의 `@Transactional(readOnly = true)` 때문에 커넥션을 잡고 `SET autocommit`/`SET SESSION TRANSACTION`/`COMMIT` 같은 트랜잭션 문장(요청당 5개)을 보낸다. 캐시가 줄이는 건 그 커넥션을 잡고 있는 시간이지, 잡는 횟수가 아니다. 풀이 포화되는 60명 이상에서 차이가 커지는 것은 이 점유 시간 때문으로 읽힌다.
- **워커:** 캐시를 끄면 채점 문항 1개당 문항 조회 SELECT가 정확히 1개다(2,507문항 → 2,507회). 켜면 0회다(처음 보는 문항 id의 첫 조회만 DB를 읽는다). 문항 하나의 처리 시간이 mock 기준 8~11초이므로 이 0.16ms는 완료 시간에 드러나지 않는다(접수→완료 p50 10.2s로 켬/끔 동일).
- 운영 의미: 설계 피크(동시 30명, 요청 사이 사용자 대기 있음)에서 캐시가 사용자 지연에 주는 영향은 1ms 미만이다. 캐시를 남길 이유는 "지연 개선"이 아니라 "정적 데이터를 요청마다 DB에 다시 묻지 않는다"는 것(요청당 SELECT 1개, 워커 문항당 SELECT 1개)과 풀이 몰릴 때의 여유다.

## 실험용 코드 (main에는 넣지 않음)

- 실험 브랜치에서만 설정 `opicnic.experiment.question-cache.enabled`(기본 true)를 두어, false면 두 캐시를 읽지도 채우지도 않고 매번 DB에서 읽게 했다. `QuestionAssemblyService.loadSets()`와 `PracticeAttemptService.questionById` 두 곳의 분기다.
- 운영 코드에 실험용 분기를 남기지 않으려고 이 설정과 실험 스크립트는 main에 합치지 않았다. 다시 재려면 위 두 곳에 같은 분기를 넣고 아래 방법대로 돌리면 된다.

## 방법

1부 start API 단독 부하(k6)
- `POST /api/practice-attempts/start`(dev 전용)만 연속 호출. 반복마다 CSRF를 새로 받는다(`s3-async.sh`와 같은 흐름). 업로드·접수·폴링 없음, 요청 사이 대기 없음(최대 부하).
- 동시 사용자 1·30·60·100, 수준마다 워밍업 10초(버림) + 30초 × 3회. 조건이 바뀔 때만 서버를 다시 띄움.
- 순서를 바꿔 두 번(시계열 편향 확인): 1차 끔 → 켬(1·30·60·100), 2차 켬 → 끔(30·60·100).
- DB 문장 수는 MySQL `SHOW GLOBAL STATUS`(`Questions`, `Com_select`)의 전후 차를 요청 수로 나눈 값. Hikari 획득 횟수는 `hikaricp_connections_acquire_seconds_count`의 차, active/pending 최대는 1초 샘플. 문장 종류별 실행 횟수는 `performance_schema` digest.
- 지속 시간을 30초로 정한 이유: 처리량이 초당 수천 건이라 수만 건이 쌓이고, 워밍업 뒤 정상 상태로 들어가는 데 충분하다. 그 이상은 이번 질문(캐시의 정상 상태 효과)에 새 정보를 주지 않고 전체 시간만 늘린다.

2부 워커 문항 조회(`scripts/s3-async.sh`로 콤보 몇 건)
- 부하 없이 콤보 몇 건만 채점. 켬은 6건으로 캐시를 채운 뒤 4건을 측정. 끔·켬 각각 digest에서 문항 조회 SELECT 실행 횟수를 센다.

## 처음 시도했다가 바꾼 것

처음에는 `s3-async.sh` 전체 흐름(start → 업로드 → 접수 → mock STT 3s + LLM 4.5s → 완료 폴링)을 1·30·60·100명 × 켬/끔 × 워밍업 + 3회로 재려 했다. 문항 하나에 8~11초의 mock 지연이 깔려 있어 밀리초 단위의 캐시 효과가 묻히고 전체가 두 시간 가까이 걸려서, 위의 start API 단독 부하 + 워커 조회 계수로 바꿨다. 1·30명 수준에서 끝낸 결과는 참고용 표 `fullflow-abandoned-table.md`로만 남겼다(원본 로그는 용량 때문에 뺐다). 그 결과에서도 start p50 4~5ms → 3ms, 접수→완료 p50 10.2s 동일, 접수 202 100%, 완료 100%로 위 결론과 맞는다(60명은 중단해 버렸다).

## 무효로 하거나 고친 것

- **다른 세션의 실험과 겹침.** 첫 전체 흐름 시도 중 13:30:52~13:39:45에 같은 머신·같은 MySQL을 쓰는 다른 opicnic 서버(PID 68738, 사용자 승인된 실험)가 돌았다. 그 시간대의 내 측정(`켬 1명` 2~3회차, `켬 30명` 일부)은 오염으로 판단해 전부 버리고, 다른 서버가 없을 때 처음부터 다시 돌렸다. 재실행에는 "다른 opicnic 서버 감지 시 대기, 구간 중 감지하면 TAINTED 표시" 점검을 넣었다. 참고용으로 남긴 전체 흐름 결과에는 TAINTED 표시가 없다. start API 단독 부하와 워커 측정은 다른 서버가 없는 상태에서 돌렸다(실행 전 `pgrep`로 확인).
- **내 정리 SQL 영향.** 겹친 구간에 내 `loadtest-cleanup.sql`이 실행되어 dev 회원 명의의 잡·결과 행을 지웠다. 다른 세션이 같은 dev 회원으로 행을 쓰고 있었다면 그 행이 지워졌을 수 있다(확인하지 못함).
- **k6 첫 버전 오류.** CSRF 토큰을 VU당 한 번만 받고 재사용했더니, 첫 start가 세션을 바꿔 두 번째 요청부터 로그인 페이지(200 HTML)가 돌아왔다. 200 검사를 통과해 6,000~19,000 req/s라는 비현실적인 수치가 나왔고, DB 문장/요청이 0.001인 것으로 알아챘다. 이 결과는 전부 버렸다. 지금은 매 반복 CSRF를 새로 받고 응답 본문에 `attemptId`가 있는지까지 확인한다.
- 1차 "켬" 서버 로그는 중간에 잘못 실행된 스크립트가 덮어써서 남아 있지 않다. 1차 켬이 캐시를 쓴 증거는 SELECT/요청 0.001과 digest다. 서버 로그의 HIT/MISS 합계는 `server-log-cache-counts.txt`(2차 켬 HIT 1,009,346 / MISS 8, 끔은 전부 MISS). 로그 자체는 크기 때문에 지웠다.

## 한계

- 부하 생성기·서버·DB가 한 머신이고 요청 사이 대기가 없어서 60~100명 수치는 "풀이 포화된 합성 부하"이지 실제 사용 패턴이 아니다. 운영의 설계 피크(30명, 사용자 대기 있음)보다 훨씬 가혹하다.
- 켬/끔을 번갈아 두 번 쟀지만 편차가 커서(위 100명 끔) 크기를 정밀하게 말할 수 없다. 방향과 DB 문장 수만 확정이다.
- 측정 topic이 QuestionSet 1개짜리다. 세트가 여러 개인 topic은 끔일 때 한 번에 더 많은 행을 읽으므로 캐시 효과가 더 클 수 있다(측정하지 않음).
- 캐시 끔 상태는 "운영 코드에서 캐시만 뺀 것"이다. 예전 메모의 "전"(워커의 `@Transactional` 포함, 500 VU)과는 다르다.
- Hibernate 통계는 켜지 않았다(켜면 오버헤드가 섞인다). DB 문장 수는 MySQL 서버 쪽 카운터이고 워커 폴링 등 배경 문장(유휴 시 초당 약 6개)이 포함되지만, start 단독 부하에서는 수만 건 대비 무시할 수 있다.
- Hikari 커넥션 획득 대기 시간은 평균만 봤다(최대는 기록하지 않음).
