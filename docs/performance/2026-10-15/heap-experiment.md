# 2026-10-15 — 힙을 줄여 놓고 옛 동기 구조와 지금 구조를 비교

> 목적: 이력서 문장 "음성을 서버 인메모리로 처리하던 구조에서 재시도 시 힙을 오래 점유 → R2 presigned 업로드로 바꿔 서버 힙 부담 감소"를 숫자로 뒷받침. 메모리가 넉넉하면 차이가 안 보여서 힙을 일부러 줄였다.
> 원본: 신 구조 쪽은 같은 폴더의 `s3-async-heap512-f45.txt`, `s3-async-new-256m-u30-s60.txt`. 구 구조 쪽(k6 출력, 힙 샘플)은 세션 스크래치패드라 repo에 없다 — 아래 표가 원본이다.

## 조건 (양쪽 동일)

- 구: 커밋 `f5cc8aa`(동기 + 인메모리, 비동기 작업 시작 직전), `scripts/s3.js`(k6). 신: HEAD `bed3fcb`, `scripts/s3-async.sh`.
- 동시 사용자 30명이 콤보를 계속 제출. 음성 4,000,000B(실제 상한 4MB). mock STT 3s + LLM 4.5s.
- 외부 API 호출당 실패 45% 주입(S2와 같은 설정: 429 30% + 5xx 10% + 타임아웃 5%).
- 서버 힙 `-Xms=-Xmx`: 512m, 256m. 별도 MySQL(3308), 호스트 하나에서 서버와 부하 생성기가 같이 돎.
- 신 구조 워커 슬롯은 기본값 60.
- 힙 지표: 1초마다 `jvm_memory_used_bytes{area=heap}` 합, 20초마다 `jcmd GC.run` 직후 값을 **live set**(GC 후 살아 있는 양)으로 기록. 최대 사용량(peak)은 G1이 꽉 찰 때까지 안 치우기 때문에 의미가 없고 live set이 비교 대상이다.

- 구 256MB의 +12%p는 OOM으로 요청이 실패한 몫. 실패한 요청은 사용자가 다시 녹음해야 한다.
- 신 구조는 접수 202 100%, 접수 응답 p95 0.035s(512MB 실행). 256MB 실행은 완료까지 511s 걸렸다 — 45% 실패 주입의 재시도 백오프 때문이며 OOM·FAILED는 없었다.

## 해석과 한계

- **줄어드는 건 "재시도 대기 중 점유"다.** 신 구조도 STT 호출 중에는 워커가 바이트를 들고 있다. 그래서 live set 상한은 슬롯 수 × 4MB(60 × 4 = 240MB)이고, 256MB 힙에서는 여유가 거의 없다. 슬롯을 줄이면 더 내려간다(안 돌림).
- 구 구조의 점유는 접속자 수에 비례해 상한이 없다(30명 × 3파일 × 4MB = 360MB, 실측 375MB).
- 각 설정 1회 측정. 편차(9/11 기록상 ±25%)는 모른다. 반복하면 더 안전하다.
- 지속 시간이 다르다(구 256m 90s, 신 512m 150s, 신 256m 90s). 비교는 live set과 실패율이라 영향이 작지만 같은 값은 아니다.
- 피크 30명은 우리가 가정한 트래픽(`slo.md` S3)이고 극한 환경이 아니다. 극한은 힙 쪽(256MB)에서 만들었다.
