# SLO — 음성 채점 서비스 수준 목표

> 작성일: 2026-09-17
> 용도: `docs/adr/0001-async-r2.md`의 전환이 "됐는지"를 판정하는 기준. 전환 전/후를 같은 시나리오로 재서 이 문서의 표를 채운다.
> 원칙: SLI는 **밖에서 관찰 가능한 값**만. 구현 세부(재시도 횟수, STT 호출 수 등)는 설계 문서와 회귀 테스트가 지키고, 여기엔 그 결과만 둔다.

## 전제

**SLO는 "원하는 서비스 수준"이지 "지금 배포에서 되는 수준"이 아니다.** 외부 API는 종량제로 한도 없이 쓸 수 있다고 놓는다 — 실제 사업이면 사용량이 늘 때 비용이 늘지 막히진 않는다. 막아야 하는 건 스팸·재시도 폭주 같은 우리 쪽 잘못이고, 그건 장애 시 SLO가 다룬다.

현재 배포(Groq 무료 티어, TPM 8K)에서 못 지키는 항목은 **배포 주석**으로 따로 적는다. 설계 문제와 제공자 제약을 섞지 않는다.

## SLO

### 사용자 1명 기준 — 규모 가정 없음

| SLI | SLO | 왜 |
|---|---|---|
| 제출 → 접수 응답 p95 | **< 500ms** | 비동기의 핵심 약속. 202만 주면 되니 동시 30에서도 수십 ms |
| 접수된 제출의 처리 완료율 | **100%** (이탈·재시작 포함) | 비동기의 존재 이유. 99%면 의미 없음 |
| 콤보 제출 → 첫 문항 결과 | **< 10s** | 문항 1건 처리 약 7.5s + 여유. 동기처럼 느끼게 |
| 모의고사 제출 → 전체 완료 | **< 1분** (정상 시) | 15문항 병렬은 mock에서 7.6s 실측(2026-09-18). 1분은 실제 제공자 꼬리 지연 + 재시도 1~2회 여유. 문항이 병렬이라 콤보와 모의고사의 완료 시간은 같다(가장 느린 문항 하나) |

### 장애 시 거동 — 우리 쪽이 폭주하지 않는 것

| SLI | SLO | 왜 |
|---|---|---|
| 외부 API 일시 장애(30분 이내) 중 접수된 문항 | **FAILED 0** — 늦어져도 끝낸다 | (2026-09-23 추가) 사용자에게 실패는 지연보다 훨씬 비싸다(다시 말해야 함). 돈·기록처럼 중복이 위험한 로직도 아니라 늦게라도 끝내는 게 맞다. 재시도는 횟수가 아니라 **시간 예산**: 일시적 실패(429·5xx·타임아웃)는 접수 후 30분까지 지수 백오프(천장 2s부터 2배, 상한 60s, 실제 대기는 0~천장 무작위(full jitter) — 2026-09-26 재시도 폭주 실험 `2026-09-26/retry-storm.md`). 영구 실패(녹음 파일 없음·깨짐)는 기다려도 안 풀리니 즉시 FAILED, LLM 형식 오류는 3회. 원래의 "3회 = 약 10초"는 사용자가 요청에 붙잡혀 있던 동기 시절의 숫자였다 |
| 외부 API 실패 45% 주입 시 우리 쪽 호출 증폭 | **≤ 1.82배** | 호출마다 실패율 p로 성공할 때까지 재시도하면 호출 수 기대값은 1/(1−p) = 1/0.55 = 1.82배. 성공한 STT는 다시 부르지 않으므로(STT·채점 각자 1.82) 설계대로면 이 값, 그 위면 재시도가 설계 밖으로 폭주하는 것. 2026-08-31 실측(STT 43건, 429 21회)의 재발 방지. (2026-09-23 변경: 3회 상한 시절엔 1 + 0.45 + 0.45² = 1.65배였다. 2026-09-18 정정: 그 전엔 "30% → 1.39 → 상한 1.5"로 주입률과 안 맞았음) |
| 외부 API 장애 중 서버 | **OOM 0, 503으로 거절** | 죽지 않는 게 최소 조건. 처리 못 하면 거절 |

### 피크

| SLI | SLO | 왜 |
|---|---|---|
| 동시 제출 30건 | 위 6개 전부 유지 | 국내 상위 영어 학습 앱(MAU 24만, 모바일인덱스 2024-11) 피크 동시 제출 추정 약 17건의 2배. 자릿수 근거이지 정밀값 아님 |

## SLO가 아닌 것

- **500VU 스트레스** — 한계 탐색. "어디서 어떻게 무너지나"를 보는 것이지 만족 조건이 아니다. 전환 전 Full GC 3회/30초(2026-09-11)와 전환 후를 같은 조건으로 비교하는 용도.
- **STT 재호출 0회, 문항별 재시도 3회 상한** — 설계 규칙. `FeedbackServiceSttRetryScopeTest`와 설계 문서 4절이 지킨다.

## 배포 주석 — 현재 Groq 무료 티어에서

| 항목 | 현재 | 이유 |
|---|---|---|
| 모의고사 전체 완료 | 약 10분 (미달) | TPM 8K. 채점 1건이 예약 약 6,000토큰이라 15문항이 한 번에 못 지나감 |
| 콤보 첫 문항 결과 | 지킴 | 3건 중 1건은 429 없이 통과 |

제공자 제약이지 설계 문제가 아니다. 종량제 전환 시 해소.

## 검증 시나리오

각 SLO에 시나리오 하나. 전부 **전환 전 / 후** 같은 조건으로.

| | 검증 대상 | 시나리오 | 통과 기준 | 어디서 |
|---|---|---|---|---|
| **S1** | 접수 응답, 완료율, 완료 시간 | 모의고사 제출 → 처리 중 **클라이언트 강제 종료** / **서버 재시작** → DB에서 15문항 완료 확인 | 접수 p95 < 500ms, 완료율 100%, 완료 < 1분 | 랩탑 |
| **S2** | 장애 시 거동 | mock에 실패 주입(STT/LLM 429 30%, 5xx 10%, 타임아웃 5%) → 콤보 50건 | 호출 증폭 ≤ 1.65배, OOM 0, 서버 살아 있음 | 랩탑 |
| **S3** | 피크 | mock 현실 딜레이(STT 3s + LLM 4.5s), 동시 30 제출, 5분 | S1 조건 유지 | 랩탑 |
| **S4** | 한계 탐색 | 500VU, delay 0 | 통과 기준 없음. Full GC 횟수·OOM·503 비율 기록 | VM |

S2의 mock 실패 모델은 **실제 429 본문**(2026-08-31, 09-02에 받은 `retry-after`, TPM 예약 메시지)으로 보정한다. 보정 없는 mock 통과는 내가 만든 장애에 내가 대응한 것일 뿐이다.

## 전/후 표 (채울 것)

"전" 열은 합격 기준이 아니다. 동기 구조엔 접수라는 단계가 없어서(응답 = 처리 완료) 500ms 같은 잣대를 댈 수 없고, 사용자가 실제로 얼마나 기다리는지를 적어 "왜 바꾸는가"의 근거로 쓴다. SLO 판정은 "후" 열만 한다.

| | 전환 전 — 동기 + 힙 (현상 기록) | 전환 후 — 오브젝트 스토리지 + 워커 (SLO 판정) |
|---|---|---|
| S1 접수 응답 p95 | 해당 없음 (응답 = 처리 완료, 대기 시간은 아래 완료 행) | 0.03~0.17s (2026-09-19~21, `s1-async-*.txt`) |
| S1 이탈 시 완료율 | 0% (finalize 전 이탈 = 전량 유실, 구조상 확정) | 100% (15/15, `2026-09-19/s1-async-smoke-kill.txt`) |
| S1 재시작 시 완료율 | 0% (Caffeine 인메모리, 구조상 확정) | 100% — 접수 직후 kill·처리 중(14개 PROCESSING) kill 둘 다 (`2026-09-19/s1-async-smoke-restart*.txt`) |
| S1 모의고사 완료 | 7.6s (2026-09-18, mock 3s+4.5s, 사용자 1명, 5회 7.58~7.62s — `2026-09-18/s1-before.txt`) | 10.3~12.4s (2026-09-21, 같은 mock + 실제 R2). +3~5s = R2 읽기 문항당 1.4s(최대 2.1) + 집기 ≤1s + 폴링 ≤2s — `2026-09-21/s1-async-timing.txt` |
| S2 호출 증폭 | 1.50배 (2026-09-18, 실패 45%, 콤보 50건 동시 5 — `2026-09-18/s2-before.txt`). 이론 상한 1.65 아래인 건 STT 성공분 재사용(9/9) 덕. 문항 실패 15.8% → 사용자 재제출 | **1.54배 / 1.45배** (2026-09-22 두 번, 같은 조건 — `2026-09-22/s2-async-after*.txt`) ✓. 접수 100/100 202(0.03~0.08s). 문항 실패 22.8% / 21.3% → FAILED 카드(재제출 없음, 재시도 API는 후속). 이론값 24%(호출 45% × STT 재사용 × 3회)와 일치 — 전환 전 15.8%가 이론보다 낮았던 이유는 미확인. 실패율 서킷(20건 중 80%)이 4회/5회 열려 30s씩 처리 정지 → 접수→완료 avg 97s/156s, max 157s/195s (2026-09-23 정정: 오작동 아님. 시도 1회 = STT+채점 두 호출이라 호출당 45% 실패면 시도 실패율 ≈ 1-0.55² ≈ 70%, 실측 189/294 = 64%. 임계 80%를 가끔 넘는 게 설계대로다) |
| S2 재시도 시간 예산 (2026-09-23) | 위 "후" 열(3회 상한): 문항 FAILED 22.8%, 증폭 1.54 | **FAILED 0/137**, 증폭 **1.83배**(이론 1.82) ✓, 접수 100% 202(0.02~0.06s). 접수→완료 avg 170s / max 567s — 옛 FAILED 문항이 끝까지 재시도해 늦게 성공한 값(시도 최대 11회). 30분 예산에 닿은 문항 없음 (`2026-09-23/s2-async-after-time-budget.txt`) |

Full GC 0, Humongous 3회(전 25회). 처리량 44콤보/분 vs 전 216/분 — 동기는 상한 없음, 비동기는 워커 슬롯 30이 상한. 슬롯 30은 피크 "동시 제출 30건"을 단위 안 맞추고 차용한 값 — 제출 30건 = 문항 ~90개(콤보)·450개(모의고사)인데 슬롯은 문항 단위. 슬롯 스윕(`2026-09-22/slots-sweep.md`): 30명엔 슬롯 60이면 큐 0, 더 올려도 완료는 안 빨라짐(문항 자체 시간이 바닥). 100명이면 접수 p95 8.5s로 약속이 깨지는데 원인은 힙이 아니라 **HikariCP 50개 전부 점유**(pending 72) — 랩탑 Docker MySQL의 느린 커밋 + 워커와 접수가 한 풀. "전" 열 중 구조상 확정인 것은 적었고, 나머지는 측정해서 채운다. 전환 전 측정은 정상 제출의 대기 시간만 재면 된다 — 이탈·재시작 시나리오는 결과가 구조상 정해져 있고, dev attempt(memberId=null)는 정상 완료해도 DB에 저장되지 않아(`FeedbackPersistenceService`) DB 검증 자체가 성립하지 않는다. 그 두 시나리오와 DB 검증은 전환 후 구현 때 dev attempt 저장 경로를 붙인 뒤 돌린다.
