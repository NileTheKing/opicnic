# 유입 속도와 처리 속도: 외부 API 장애와 시즌 피크 (2026-10-21, 계획)

질문: 피크에 외부 API가 죽었다 살아나면 밀린 문항이 언제 다 빠지나. 서킷, 백오프, full jitter, 속도 제한은 각각 어느 상황을 맡나.

2026-09-26 재시도 폭주 실험(`../2026-09-26/retry-storm.md`)은 제공자 한도(초당 10건, 1초 창)가 우리 처리 속도보다 작은 조건을 처음부터 깔았다. 이번에는 현실적인 유입과 한도에서 다시 잰다. 기존 실험의 측정값은 비교에 쓰지 않는다.

## 가정 (확정)

| 가정 | 값 | 근거 |
|---|---|---|
| MAU | 24만 | 국내 상위 AI 스피킹 앱 수준 (모바일인덱스 2024-11) |
| DAU/MAU | 25% | 듀오링고 2025년 36~37%보다 보수적으로. 시험 준비 앱은 쓰는 기간엔 매일 온다 |

| 피크 집중 | 저녁 3시간에 하루의 40% | 가정 |
| 제출 종류 | 콤보 60% (평균 2.8문항, 실측) / 유형 연습 30% (1문항) / 모의고사 10% (15문항) | 가정. 제출당 기댓값 3.5문항 |
| 시즌 배수 | 공채 시즌 x2 | 가정. 응시자 증가 공개 자료를 찾으면 교체 |

| 제공자 한도 | STT 분당 2,000 / LLM 분당 4,000 (분 단위로 셈) | 평소 피크 필요량(STT 1,400, LLM 2,800)의 약 1.45배. OpenAI STT Tier 2, Gemini Flash-Lite 유료 Tier 1 수준 |

## 계산

```
DAU 6만 x 하루 3회            = 하루 18만 건
저녁 3시간에 40%               = 7만 2천 건 / 10,800초 = 초당 6.7건 제출
x 제출당 3.5문항               = 초당 약 23문항 유입 (시즌 46)
필요 슬롯 = 23 x 8초           = 약 190 (시즌 약 380)
STT 필요량 = 23 x 60           = 분당 약 1,400 (시즌 2,800 → 한도 2,000 초과)
LLM 필요량 (채점 + 태깅)       = 분당 약 2,800 (시즌 5,500 → 한도 4,000 초과)
```

```
처리 속도 = min(슬롯 / 문항당 시간, 제공자 한도)
장애 중   : 처리 속도 0 → 초당 23문항씩 쌓임 (5분이면 약 6,900)
복구 후   : (처리 속도 - 23)으로 줄어듦 → 슬롯 여유가 복구 시간을 정한다
```

## 단계

| 단계 | 조건 | 볼 것 | 맡는 장치 |
|---|---|---|---|
| 1 | 평소 피크(초당 6.7건 제출), 장애 없음. 슬롯 60 / 200 / 300 | 접수 응답(서버 측 평균·p95, 이력서 숫자), 실제 처리 속도, 대기 줄, 접수→완료, 힙, DB 커넥션 | 슬롯 |
| 2 | 평소 피크 + 5분 완전 장애(전부 503) 후 복구. 한도는 넉넉하게(429 배제). 슬롯은 1단계에서 고른 값 | 장애 중 헛호출 수(서킷 끔 vs 켬), 밀린 문항이 다 빠지는 시간, 그중 백오프 대기 몫 | 서킷, 슬롯 여유 |
| 3 | 시즌 피크 + 제공자 용량 감소 | 429, 헛호출, 대기 줄, 접수→완료 p95, 정상 복귀 시간 | 아래 사다리 |

### 3단계 설계 (2026-10-22 확정)

- 부하: 시즌 피크 초당 46문항. 한도는 시즌을 감당하는 등급 STT 분당 5,000 / LLM 분당 10,000(시즌 필요량의 약 1.8배).
- 2분 뒤 제공자 용량이 40%(STT 2,000 / LLM 4,000)로 떨어져 5분 유지 후 회복. 우리 token bucket은 원래 한도만 안다.
- 효과를 분리하려고 일부러 한 겹씩 쌓은 사다리다(실제 코드의 과거 상태가 아니다. 실제 코드는 처음부터 지수 백오프였고 2026-09-26에 full jitter로 바꿨다).

| 단계 | 설정 |
|---|---|
| L0 | 즉시 재시도 |
| L1 | 지수 백오프 (jitter 없음) |
| L1.5 | 지수 백오프 + 작은 jitter(1초 미만) |
| L2 | 지수 백오프 + full jitter (현재 코드) |
| L3 | L2 + token bucket (고정 한도) |
| L4a | L3 + AIMD (429를 맞으면 절반, 성공이 이어지면 조금씩 올림) |
| L4b | L3 + 헤더 방식 (가짜 제공자가 남은 한도·리셋 시각·Retry-After 헤더를 준다) |

L4를 둘로 나눈 이유: 2026-10-21 Gemini 실제 호출(성공 200) 응답에 한도 헤더가 없었다(429 본문의 retryDelay는 알려진 바일 뿐 직접 확인 못 함). OpenAI·Groq는 응답마다 남은 한도 헤더를 준다. 제공자가 주는 정보에 따라 맞는 방식이 다르다.

2단계에서 full jitter는 켠 채 고정(429가 없어 할 일이 없다). 대신 복구 시간 중 백오프 대기(상한 60초) 몫을 따로 기록한다.

3단계 메모: 시즌 유입(초당 46문항)은 STT 한도 분당 2,000(초당 33)을 넘어 장애가 없어도 쌓인다. 속도 제한기는 429를 대기 줄로 바꿀 뿐 이건 못 막는다 → 시즌엔 등급을 올렸다고 가정(STT Tier 3 분당 5,000)하고, 제공자가 갑자기 용량을 줄이는 상황을 본다. 슬롯은 동시 개수를 제한할 뿐이라 빠른 실패(503 즉시 응답) 때는 보내는 속도가 막히지 않는다.

## 실행 런북 (2026-10-22 밤, 유저 부재 중 혼자 진행)

실행은 Sonnet 에이전트가 이 문서만 보고 한다. 대화 맥락은 없으므로 여기 적힌 것만 기준으로 하고, 적혀 있지 않은 판단이 필요하면 멈추고 "결정 필요" 목록에 적는다. 진행 상황은 이 문서 끝 "진행 기록"에 단계마다 덧붙인다(어디까지 했는지, 실행별 원본 파일 경로).

유저가 승인한 범위: 1, 2, 3단계 구현과 실행 전부. 유저는 자리에 없다. 끝나면 결과 문서를 남긴다.

### 1단계 슬롯 고르는 기준
대기 줄이 계속 늘지 않음 + 접수 p95 ≤ 0.5s + 접수→완료 1분 이내(콤보·모의고사) + 힙·DB 커넥션 여유. 만족하는 가장 작은 값. 60은 부족 기준선, 300은 2단계 복구 비교 재료.

### 실행 형식
- 1단계: 실행마다 1분 예열 + 5분 측정. 2단계: 예열 1분 → 5분 완전 장애 → 복구 후 대기 줄이 0이 될 때까지(상한 20분) 계속 유입.
- 3단계: 예열 2분 → 용량 40% 5분 → 회복 후 정상 복귀까지(상한 15분).
- 부하는 open model(k6 `constant-arrival-rate`, 완료를 기다리지 않음). 제출 종류는 콤보 60 / 유형 연습 30 / 모의고사 10을 무작위로 섞는다. 업로드 포함.
- 측정: 서버 측 접수 응답(http_server_requests 202), 클라이언트 측 접수 응답, 202 비율, 큐 깊이·처리 중(5초 샘플), 접수→완료(실험 DB의 scoring_job created_at → completed_at), 외부 호출 수(opicnic_external_call_seconds_count, outcome별), 힙, HikariCP active/pending, 실행 전후 axon·운영 앱 CPU와 VM 여유 메모리.

### 변수 통제 (실행마다)
- 실험 앱을 새로 띄운다(서킷·캐시·메모리 저장소·지표 카운터 초기화). 예열 구간(1단계 1분, 2단계 1분, 3단계 2분)은 평소 부하로 돌리고 숫자는 버린다.
- 실험 DB의 scoring_job, scoring_job_item, feedback_result, feedback_tag를 비우고 시작(문제 테이블은 유지).
- 가짜 제공자 한도·용량 비율·장애 스위치를 기본값으로 되돌리고 시작. 장애·용량 감소는 스크립트가 시각에 맞춰 켜고 끈다(손으로 하지 않는다).
- 제출 종류는 무작위가 아니라 고정 순서 반복: 10건마다 콤보 6, 유형 연습 3, 모의고사 1(예: C T C C T C M C T C).
- 1, 2단계는 실행마다 R2 `opicnic-exp`를 비운다.
- 시작 전에 axon·운영 앱 CPU가 조용한지 확인(합계 CPU 10% 미만이 1분 유지), 실행 내내 5초 간격 기록.

### 반복
- 1단계: 설정마다 2번. 2단계: 설정마다 3번. 3단계: 설정마다 2번, 두 번의 핵심 값(정상 복귀 시간, 429 수) 차이가 20%를 넘으면 3번째.
- 순서를 섞는다: 첫 바퀴는 정순, 두 번째 바퀴는 역순(예: 3단계 L0→L4b, 다음 L4b→L0).
- 결과 표에는 평균만이 아니라 실행별 값을 다 적는다. 차이가 크면 한계에 남긴다.
- 시간이 모자라면 반복을 줄이지 말고 3단계 실행을 다음으로 넘긴다.

### 환경 구성

- 실험 앱: `SPRING_PROFILES_ACTIVE=dev`, mock 제공자(STT 3초, LLM 4.5초), 힙 3GB 안팎, 포트는 VM 루프백만. 실험 DB: 별도 mysql 컨테이너.
- 문제 데이터: 운영 DB에서 question_set, question, combo, combo_question_types 4개 테이블만 읽기 전용 덤프해 실험 DB에 넣는다.
- 저장소: 1, 2단계는 R2 `opicnic-exp` 버킷(실행마다 비움). 3단계는 메모리 저장소. 이유: 시즌 부하는 업로드 요청이 많아 R2 쓰기 요청 무료 한도(월 100만 건)를 크게 쓰는데 3단계의 변수는 저장소가 아니다.
- 녹음 파일: 로컬 `~/Downloads/exp_recording.webm`(유저 목소리, 저장소 커밋 금지)을 VM 실험 폴더로만 복사.
- 부하 생성기: VM 안 docker `grafana/k6`.

### 3단계 코드 (설정으로 켜고 끔, 기본값은 지금 동작 그대로)
- 가짜 제공자: STT와 LLM을 따로 분당 한도(토큰 버킷 방식)로 세고, dev 스위치로 용량 비율을 바꾼다. 거절은 즉시 429. 헤더 모드에선 남은 한도·리셋 시각·Retry-After를 준다.
- 재시도 방식 설정: 즉시 / 지수 / 지수 + 1초 미만 jitter / 지수 + full jitter(기본).
- 우리 쪽 속도 제한기(Bucket4j): 외부 호출 직전에 토큰을 받는다. 모드: 끔(기본) / 고정 / AIMD / 헤더.
- 단위 테스트로 기본값이 지금 동작과 같은지 확인하고, 전체 테스트를 CI 조건(CI=true)으로 통과시킨 뒤 로컬 커밋.

세부 규칙:
- 재시도 방식 설정 `opicnic.worker.backoff-mode`: `immediate`(대기 0, 다음 폴링에 다시 집음) / `exponential`(2s부터 2배, 상한 60s, 429는 4s부터, 무작위 없음) / `exponential-small-jitter`(위 + 0~1초 무작위) / `full-jitter`(기본, 지금 `ScoringWorker.backoff`). 기존 `backoff-enabled=false`는 `immediate`와 같다.
- 속도 제한기 `opicnic.outbound.limiter.mode`: `off`(기본) / `fixed` / `aimd` / `header`. 종류별(stt, llm) 분당 한도 `opicnic.outbound.limiter.stt-per-minute`, `llm-per-minute`. 토큰은 STT 호출 전 stt 1개, 채점·태깅 호출 전 llm 1개씩. 토큰이 없으면 가상 스레드에서 기다린다(대기 상한 30초, 넘으면 일시적 실패로 처리).
- AIMD: 429를 받으면 현재 속도를 절반(최소 원래 한도의 10%), 1초 동안 429가 없으면 원래 한도의 2%씩 올림(상한 원래 한도). 
- 헤더: 가짜 제공자가 응답마다 `x-ratelimit-remaining-requests`, `x-ratelimit-reset-requests`(초), 429에는 `Retry-After`(초)를 준다. 제한기는 남은 수 / 리셋까지 시간으로 속도를 맞추고, 429면 해당 문항 다음 시도를 Retry-After 이후로(full jitter 대기와 큰 쪽).
- 가짜 제공자 한도는 종류별 토큰 버킷(분당 한도, 1초마다 한도/60씩 채움, 최대 버스트 = 한도/60 x 5). 용량 비율 스위치는 dev 엔드포인트(`/api/practice-attempts/mock-provider`에 `sttPerMinute`, `llmPerMinute`, `capacity` 파라미터 추가). 기존 `limitPerSecond`는 그대로 둔다.

### 하지 않는 것
push, 운영 배포, 운영 앱·운영 DB 변경(문제 테이블 읽기만), axon 컨테이너, 이력서 수정(숫자만 정리), 포트로 프로세스 kill.

### 중단 조건

- 한계: 슬롯 500의 이론 여유는 16문항/s(62.5 - 46)다. 관측된 회복 후 실제 처리 속도는 50~55문항/s(이론 62.5의 약 85%)라 장애 뒤 밀린 줄을 빼는 순 속도는 약 9문항/s에 그쳤다. 아래 결과의 "정상 복귀가 15~25분"은 거의 이 값에서 나온다. 슬롯을 더 올리면(예: 700) 복귀가 짧아진다. 이번에는 권장값 500으로 고정했다.

### 메모리 저장소 (오디오가 쌓이지 않게)

R2 대신 인메모리 저장소를 쓰되 업로드가 앱을 지나야 해서 dev 전용 `PUT /api/dev/audio/**`(`DevAudioUploadController`)를 추가했다. 그대로 두면 46문항/s x 1.36MB로 몇 분 만에 수십 GB가 쌓이므로 `InMemoryAudioStorage`가 내용 해시(SHA-256)가 같은 오디오를 한 번만 보관하고(키마다 같은 배열을 가리킨다) 서로 다른 내용의 총량이 256MB를 넘으면 거절한다. 실험 녹음은 하나뿐이라 보관량이 1.36MB로 고정되고 키 맵만 문항 수만큼 늘어난다. 확인: 스모크와 본 실행 15회 내내 호스트 여유 메모리 최소 4.76GB(2GB 중단 기준 이상), 힙 사용 3.07GB 이하.

### 해석

- **접수 응답은 시즌 규모와 용량 감소에서 흔들리지 않는다.** 초당 46문항, 제출 13.2건/s에 업로드까지 앱을 지나는데도 서버 측 평균 약 15ms, p95 26~28ms이고 접수 202가 100%다. 접수가 DB 저장만 하고 외부 호출을 기다리지 않아서 제공자가 용량의 40%로 줄어도, 대기 줄이 1만 2천까지 쌓여도 같다. 1단계(초당 23문항 평균 18ms, p95 35ms)보다 오히려 낮은데 이번엔 업로드가 R2 왕복이 아니라 메모리 저장소로 가고 mock이라서일 가능성이 크다(새 규모에서도 "접수는 느려지지 않는다"가 확인된 것이고, 이 숫자를 저장소 지연까지 포함한 운영 값으로 쓰면 안 된다).
- **L0에서 L2까지는 구분되지 않는다.** 429 수 1.68~1.96천, 복귀 1.3~1.45천 초로 회차 간 변동(8~10%) 안에 있다. 이유: 거절이 즉시 429라 슬롯이 바로 풀리고, 무엇보다 서킷이 감소 구간 60개 표본 중 54개(약 90%)에서 열려 있어 "언제 다시 집느냐"를 백오프가 아니라 서킷이 정한다(감소 중 처리 속도 약 9문항/s, 제공자가 받아줄 수 있는 STT 초당 33건과 필요 46건에 한참 못 미친다). 이 조건에서는 즉시, 지수, jitter, full jitter 방식 사이의 차이를 이 설계로는 보지 못했다. 2026-09-26 실험(한도가 처리 속도보다 작고 서킷이 없던 조건)에서 본 jitter의 효과가 서킷이 있는 지금 구조에서는 가려진다고 읽어야 하고, "jitter가 쓸모없다"는 결론이 아니다.
- **감소 중 대기 줄은 모든 단계에서 약 1만 건이 쌓인다.** 필요량 46문항/s와 제공자가 받는 33문항/s의 차이는 13문항/s라 5분이면 약 3,900건인데 실제는 10~11천 건(회복 시점 5,730~10,998)이다. 쌓이는 속도의 대부분은 서킷이 30초씩 열려 처리 자체가 멈추는 데서 나온다. 회복 직후 약 120초는 서킷이 남아 있거나 속도 제한기가 낮은 값이라 대기 줄이 더 늘다가(최대는 감소 시작 후 304~334초) 이후 초당 약 9건씩 직선으로 빠진다(기울기 -8.3~-9.4건/s).
- **정상 복귀는 20분을 넘는다(L4b 제외).** 순 감소 속도가 약 9건/s(처리 50~55 - 유입 46)라 1만 건이 넘는 줄을 빼는 데 약 20분 이상이 든다. 이론 여유는 16건/s였는데 실제 처리가 이론의 85%라 그렇다. 슬롯이 정하는 값이고 사다리 단계가 정하는 값이 아니다. 앞의 (슬롯 선택, 한계) 참고.
- **L3(고정 token bucket)은 효과가 작다.** 429가 1.47천으로 L2(1.8천)보다 약 19% 적고 복귀도 약 6% 짧지만 서킷 열림은 같다(54 / 54). 이유: 고정 한도 5,000 / 10,000은 제공자가 용량을 줄이기 전 값이라 감소 중(2,000 / 4,000)에는 한도를 넘겨 보내 429를 계속 맞는다. 고정 한도는 "평소 한도를 실수로 넘는 것"을 막지, 갑자기 줄어든 용량은 못 막는다. 이 설계가 이미 예상한 한계다(우리 쪽 token bucket은 원래 한도만 안다).
- **L4a(AIMD)는 429를 약 64% 줄이지만 복귀는 거의 같다.** 429가 653(L2의 약 36%)이고 감소 중 접수된 잡의 접수→완료 p95가 372초에서 235초로 줄었다(요청 하나가 버리는 시간이 줄어든 것). 대기 줄 최대는 1.09만(L2 1.2만)으로 조금 낮다. 그러나 복귀 1269초는 L2(1335초)와 5% 차이뿐이다. 이유: 429를 맞으면 절반으로 줄고 1초마다 한도의 2%씩만 올려서 감소 구간 내내 톱니로 오르내리고(관찰한 최소 STT 속도 분당 500 = 한도의 10%), 회복 뒤에도 원래 한도까지 되올라오는 데 시간이 걸린다(1초에 2%씩이면 최소 속도에서 한도까지 약 45초). 서킷 열림은 43~48 / 54로 여전히 많다. AIMD는 "헛호출을 줄이는" 도구이고 "밀린 줄을 빨리 빼는" 도구는 아니다.
- **L4b(헤더 방식)가 429와 복귀 시간을 모두 가장 크게 줄였다.** 429 평균 249로 L2의 14%, 복귀 평균 817초(약 13.6분)로 L2의 약 61%, 대기 줄 최대 평균 7.1천(L2 12.1천), 서킷 열림 8~30 / 54(L0~L3은 54). 제공자가 남은 한도와 리셋 시각을 매 응답으로 알려주니 속도를 실제 용량(초당 33건)에 맞춰 보내 429로 서킷이 열리는 일이 드물고 그만큼 처리가 계속된다. 감소 중 접수된 잡의 접수→완료 p95도 372초에서 146~181초로 줄었다. 단 이것은 mock이 헤더를 정확히 주는 조건이다. 2026-10-21 Gemini 실제 호출 응답에는 한도 헤더가 없었으므로(OpenAI와 Groq는 줌) 제공자가 헤더를 주지 않으면 이 방식은 쓸 수 없고 L4a나 L3로 돌아간다. 사다리에서 "무엇이 가장 낫다"가 아니라 "제공자가 주는 정보가 방식을 정한다"로 읽어야 한다.
- 외삽 검증: 20분 관찰 6회(L0~L4a 회차 1)에서 같은 방식으로 1100초 시점 대기 줄을 예측한 값과 실제를 비교하면 예측이 실제보다 조금 크다(L0 2509 / 2396, L1 2920 / 2362, L1.5 2239 / 1981, L2 2340 / 2248, L3 789 / 583, L4a 1635 / 1267). 남은 줄의 오차를 기울기(-9건/s 안팎)로 나눈 시간 오차는 10~60초로 외삽 복귀 시간(1200~1450초)의 1~5%다. 외삽은 실제 복귀 시간을 약간 길게 잡는 보수적인 값이다. L3 회차 1은 유일하게 관찰 상한 안에서 평소 수준 기준 실측 1154초에 도달했고 같은 회차의 외삽(0까지) 1188초와 3% 차이다.
- 자원: 힙 최대 2.85~3.07GB, Hikari 활성 연결은 최대 50 중 한 자릿수에서 십수 개 안팎이고 대기 0(스모크 기준), 호스트 CPU 평균 32~39%, 운영 앱 ERROR 0. 앱 ERROR 로그 17~68줄은 대부분 워커 폴링의 DB 교착(1단계에서 본 것, 회차당 6~29)과 서킷 OPEN 로그다.

### 한계

- 사다리 L0~L2가 서킷 때문에 구분되지 않는다. 백오프 방식의 효과를 따로 보려면 서킷을 끄고 돌려야 하는데 이번 계획(서킷 켬 고정)에서 벗어나 하지 않았다.
- 순수 mock이고 응답이 정확히 규칙적이다(STT 3초 / LLM 4.5초 고정, 헤더가 정확). 실제 제공자의 지연 분포와 헤더 오차를 반영하지 않는다. 특히 L4b의 이점은 mock의 이상적인 헤더에 의존한다.
- 복귀 시간은 대부분 외삽이다(6분 또는 20분 관찰). 회복 후 곡선이 직선이라는 가정이며 L0~L3 회차 1(20분 관찰)에서 검증했고 오차는 1~5%다. L4a와 L4b는 회복 곡선이 처음 약 120초 동안 비직선이라 직선 구간(120~300초)만 썼다. 6분 관찰 회차의 접수→완료 p95는 못 끝난 잡이 빠진 값이다.
- 처리 능력은 슬롯 500에서 이론의 약 85%라 순 감소 속도가 약 9건/s로 낮다. 그래서 복귀 시간 절대값은 20분 안팎이고, 슬롯이 더 크면 모든 단계의 복귀가 짧아지고 단계 간 비율도 달라질 수 있다.
- 회차 간 변동: L4b 회차 1, 2는 복귀 차이가 20.4%(3번째로 보강), 나머지는 2~11%. 429 수의 회차 간 변동은 7~12%.
- k6 `urls` 실패(upload-urls가 비 200)가 20분 관찰 회차에서 0~15건(약 2만 건 중, 0.08% 이하) 있었다. 접수 202 비율에는 영향이 없다. 시도 캐시(Caffeine, 최대 1만 건)가 가득 차는 시점 이후에만 보이므로 캐시 축출로 추정하지만 확인하지 않았다.
- 새 DB로 처음 기동한 첫 접수 몇 건에서 dev 전용 `dev-tester` 회원 중복 생성 500이 났다(스모크에서 4건, 동시 첫 요청 경합). 예열 구간 안에서 끝나 본 실행 숫자에는 영향이 없었다.
- 앱 ERROR의 교착(Deadlock) 로그는 1단계에서 본 것과 같은 현상이고 원인 분석은 하지 않았다(후속 확인 후보).

## 이력서용 숫자 요약

- **새 규모(초당 46문항, 제출 13.2건/s, 업로드 포함) 기준 접수 응답:** 서버 측 평균 약 15ms, p95 약 27ms(15회 범위 평균 14.6~16.0ms, p95 25.8~27.9ms), 접수 202 100%. 제공자가 용량의 40%로 줄어 대기 줄이 1만 2천 건까지 쌓이는 중에도 같다. 평소 규모(초당 23문항)에서는 평균 약 18ms, p95 약 35ms(슬롯 200, 1단계). 접수는 DB 저장만 하고 외부 호출을 기다리지 않아서다.
- **서킷 효과(2단계, 5분 완전 장애, 초당 23문항):** 장애 중 실패 호출 약 1.9만 건에서 약 1.8천 건으로 약 10배 감소(STT는 약 1.7만 건에서 약 1.5천 건). 비용은 복구 후 서킷이 열려 있는 약 35초 동안 집지 않아 복구가 그만큼 늦어지는 것. (3단계에서도 서킷은 용량 감소 구간의 약 90%에서 열려 있었다. 이때 호출은 더 안 나가지만 처리도 감소 중 초당 약 9문항으로 떨어졌다.)
- **3단계 사다리(시즌 초당 46문항, 제공자 용량 40%로 5분 감소 후 회복):** 429 수는 즉시 재시도, 지수 백오프, jitter, full jitter가 약 1.8천 건으로 사실상 같고(서킷이 집는 속도를 정해서), 고정 token bucket 약 1.5천(-19%), AIMD 약 650(-64%), 헤더 방식 약 250(-86%). 대기 줄이 평소로 돌아오는 시간은 약 22분에서 헤더 방식 약 13.6분(-39%)으로, 대기 줄 최대는 1.2만에서 0.7만으로 줄었다. 고정 token bucket과 AIMD는 429는 줄여도 복귀는 5~6% 개선에 그쳤다. 제공자가 한도 헤더를 주는지가 방식을 가른다.

## 계획과 달라진 것

- 3단계 회복 관찰: 계획의 상한 15분(런북) 대신 처음 20분으로 시작했다가(L0~L4a 회차 1 6회) 유저 요청으로 6분(MAX_RECOVER_S=360)으로 줄였다(회차당 29분에서 약 15분). 변경 시각은 L4a 회차 1 진행 중(KST 2026-10-22 08:25 무렵, 이후 L4b 회차 1부터 적용). 줄인 구간의 정상 복귀 시간은 회복 후 120~300초 대기 줄 기울기로 0까지 선형 외삽했다. 20분 관찰 회차에서 외삽 오차를 검증했다(위 해석). 반복 규칙(핵심 값 차이 20% 초과 시 3번째)은 외삽값 기준으로 적용했다.
- 슬롯: 계획의 "1단계에서 고른 값(200)" 대신 시즌 유입에 맞춰 500(스모크로 확인).
- 메모리 저장소 구현: 계획은 단순히 "메모리 저장소"였지만 업로드가 앱을 지나야 해서 dev 전용 업로드 엔드포인트를 만들었고, 오디오를 내용 해시로 공유하게 했다.
- 제한기 세부(문서에 없던 판단): AIMD는 429 연속 도착에 대해 1초에 한 번만 절반으로 줄인다(모든 429마다 줄이면 한 번의 폭주에 바닥까지 떨어짐). 헤더 방식 속도 = 남은 수 / 리셋까지 시간을 분당 한도의 10%~100%로 자르고 200ms마다 한 번만 반영. 헤더의 리셋은 "버킷이 다 찰 때까지 초"(가짜 제공자 정의). 제한기 대기 초과(30초)는 새 사유 `LOCAL_LIMIT`로 일시적 실패 처리하되 워커 서킷에는 세지 않는다(스모크에서 제한기 대기 초과가 서킷을 열어 제공자가 멀쩡해도 30초 멈추는 것을 보고 고침).
- 가짜 제공자 버킷은 1초 단위로 채움(문서대로), 용량 비율을 바꾸면 현재 토큰을 새 상한으로 자르고 한도 값 자체가 바뀌면 가득 찬 상태로 시작.
- 정상 복귀 정의: 계획은 "평소 수준"이었고 실제 판정은 복구 전 30초 평균 + 50% + 20건 이하 3표본 연속을 유지하되 결과 표는 0까지 외삽 기준.
- 스모크 3회(`smoke3-*`, 슬롯 500 정상 부하, L4b와 L4a 축소판)는 표에 넣지 않았다.
