# 워커 동시 상한(슬롯) 산정 스윕 — 2026-09-22

질문: `opicnic.worker.concurrency`(지금 30)는 피크 "동시 제출 30건"을 문항 단위로 안 바꾸고 차용한 값이다. 얼마가 맞나, 올리면 우리 쪽 어디가 먼저 무너지나.
방법: `scripts/s3-async.sh`(N명이 5분간 접수→완료 대기→다음 반복)를 슬롯을 바꿔가며. **부하는 콤보만**(MOVIE_WATCHING/LEVEL_3, 2~3문항, 실측 평균 2.8문항/제출). 모의고사(15문항)는 안 섞었다 — 모의고사 피크 30건이면 문항 450개라 같은 논리로 슬롯이 5배 필요하지만, 그 전에 커넥션 풀이 먼저 고갈된다(아래 2). 랩탑, mock 지연 STT 3s + LLM 4.5s, 실제 R2, MySQL 3307, HikariCP 기본 10. 부하 생성기(curl/jq 프로세스 N개)가 서버와 같은 랩탑 — 100명 조합은 CPU·네트워크를 서버와 나눠 쓴 값이다.

## 읽기

1. **피크 30명(콤보) 기준 슬롯 60이면 큐가 사라진다** (max 40 → 0). 120으로 더 올려도 완료는 안 빨라진다 — p50이 셋 다 12.3s 언저리. 바닥은 큐 대기가 아니라 문항 자체 시간이고, 그중 R2 읽기가 단독 1.4s → 30명 동시엔 3.3~3.8s로 늘어난다(랩탑 네트워크에서 동시 읽기).
2. **100명이면 접수 약속이 깨진다 (p95 8.5~8.8s, SLO 0.5s).** 힙·GC는 멀쩡(Full GC 0). 무너진 곳은 **DB 커넥션 풀(10개)** — HikariCP pending 72. 워커 트랜잭션(문항 조회·STT 저장·마무리)이 풀을 다 물고 있어 접수(`POST /api/scoring-jobs`가 잡 행을 쓰는 것)가 커넥션을 기다린다. 접수와 워커가 한 풀을 쓰는 게 구조적 문제: 워커가 바쁠수록 접수 약속이 늦어진다.
3. 100명에선 R2 읽기가 avg 12~14s, max 70s로 튀고 mock의 고정 지연(3.0/4.5s)마저 4.7~6.9s로 늘어난다 — 부하 생성기 100개와 서버가 한 랩탑을 나눠 쓴 흔적. 이 조합의 완료 시간은 VM(S4)에서 다시 재야 한다. 접수 p95 8s는 커넥션 풀 고갈이 원인이라 VM에서도 재현될 것.

## 결정

- 슬롯 기본값 30 → **60** (피크 30명 큐 없음, 랩탑 실측). `application.yml` 기본값 변경.
- 접수 경로를 워커의 DB 사용에서 보호하는 것이 다음 과제(backlog): 풀 확대(10 → 슬롯 수와 비례) + 워커 트랜잭션이 한 번에 쓸 수 있는 커넥션 상한, 또는 접수용 풀 분리. 그 뒤에 100명 조합 재측정.
- 슬롯 산정의 일반식: 큐 없음 조건은 슬롯 ≥ 피크 동시 제출 × 제출당 문항 수(콤보 3, 모의고사 15). 목표는 큐 0이 아니라 완료 SLO(모의고사 1분)라, 한 번에 N문항이 오면 마지막 완료 ≈ N/슬롯 × 9s ≤ 60s → 모의고사 피크 450문항엔 슬롯 ≥ 68, 여유 두면 90. 60은 콤보 피크만 큐 0. 실제 상한은 커넥션 풀이 먼저 정한다.

## 측정 도구에서 잡은 것
- 서버 교체 시 옛 서버의 graceful shutdown 중에 `/actuator/health`가 UP을 돌려줘 부하가 죽는 서버로 갔다(두 조합 무효 → 재실행). 새 프로세스 로그의 `Started OpicnicApplication`을 기다리도록 수정.
- macOS awk가 Prometheus의 `1.7E7` 표기를 숫자로 못 읽어 힙 샘플이 0으로 찍혔다 → actuator JSON으로.
- 스크립트가 R2 PUT 응답을 확인 안 하고 접수해 "key does not exist" FAILED가 섞였다(u100/120에서 10건) → 브라우저와 같은 규칙(PUT 실패 시 접수 안 함)으로 수정. 이 FAILED는 제품 결함이 아니다.
